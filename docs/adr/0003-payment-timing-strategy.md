# ADR 0003: 결제 시점/방식 결정 — 참여 시 선결제 vs 목표 달성 후 결제

- 상태: 채택됨 — B(목표 달성 후 결제) 확정, 정산 배치 트랜잭션 분리 설계는 별도 Plan Mode 세션으로 진행
- 작성일: 2026-09-21
- 관련 이슈: #9
- 관련 ADR: [0001-concurrency-control-strategy.md](./0001-concurrency-control-strategy.md), [0002-deadline-settlement-batch-concurrency.md](./0002-deadline-settlement-batch-concurrency.md)

## 배경

현재 `OrderService.participateGoodsFunding`(`orders/service/OrderService.java` 35행 부근)은
`Orders`만 생성하고 결제 도메인을 전혀 호출하지 않는다. `Payment` 엔티티(`payment/domain/Payment.java`)는
`Orders`와 1:1(unique `order_id`)로 스키마만 존재하고, 생성 시 `status`가 항상 `REQUESTED`로 시작하는
구조만 정의돼 있을 뿐 어디서도 사용되지 않는다. ADR-0002 배경에도 "환불 로직은 이번 이슈 범위에서
제외한다 — `Orders`에 `paymentStatus`가 없고 결제 도메인이 구현되지 않아 환불할 대상 데이터 자체가
없다"고 명시적으로 후속 이슈로 미뤄둔 상태다. 이 ADR이 그 후속 결정이다.

결정해야 할 것은 "PG 결제 승인 API를 언제 호출하는가"이며, 이는 CLAUDE.md 금지 패턴인
**"트랜잭션 안에서 외부 API를 동기 호출하지 않는다"**가 정확히 어느 트랜잭션 경계에 적용되는지,
그리고 ADR-0001(참여 시 비관적 락)·ADR-0002(미달 공구 종료 잡의 상태 전이 트랜잭션)가 이미 확정한
두 트랜잭션 중 어느 쪽에 결제 호출이 인접하게 되는지를 바꾼다. 아직 코드가 없는 그린필드
결정이라 ADR-0001/0002처럼 실측 벤치마크를 먼저 돌릴 대상이 없고, 이번 초안은 두 구조의
정합성·장애 지점을 비교하는 데 집중한다. 실측이 필요한 하위 결정(예: 정산 배치의 결제 fan-out
처리량)은 이 ADR에서 방향이 정해진 뒤 별도로 진행한다.

## 비교 대상

### A. 참여 시 선결제 (Pay-at-join) — 실패 시 자동 환불

- 참여 흐름: 참여 요청 → PG 결제 승인 API 동기 호출(ADR-0001의 `findByIdForUpdate` 트랜잭션 **밖**에서 먼저 수행) → 승인 성공 시에만 재고 차감 트랜잭션 진입, `Payment.status`를 `SUCCEEDED`로 갱신.
- 마감 미달(`FAILED`) 시: 정산 배치가 해당 `GoodsFunding`에 속한 `Orders`/`Payment`를 모두 조회해 환불 API를 각각 호출.
- PG 호출 시점: 참여가 들어올 때마다 분산됨 — 미달 공구 종료 잡 자체에는 결제 호출이 없다(환불 호출만 추가됨).

### B. 목표 달성 후 결제 (Charge-on-settlement)

- 참여 흐름: 참여 시점엔 결제수단 등록/토큰화만 수행(재고 차감 트랜잭션 안에 PG 호출 없음 — 금지 패턴을 구조적으로 피함).
- 마감 시 목표 달성(`FINISHED`) 확정 후: 정산 배치가 해당 `GoodsFunding`의 참여자 전원에게 결제 승인 API를 일괄 호출(fan-out).
- 마감 미달(`FAILED`) 시: 결제 자체가 발생한 적이 없으므로 환불 로직 불필요.

## 비교

| 기준 | A. 선결제+환불 | B. 달성 후 결제 |
|---|---|---|
| PG 호출과 재고차감 트랜잭션(ADR-0001)의 관계 | PG 호출을 트랜잭션 밖에서 먼저 끝내야 함(순서 강제 필요) | 트랜잭션에 PG 호출 없음(자연히 분리) |
| PG 호출과 미달 공구 종료 잡 트랜잭션(ADR-0002)의 관계 | 없음(종료 잡은 상태 전이만) | 정산 배치가 상태 전이 **직후** 참여자 수만큼 PG 호출을 책임져야 함 — ADR-0002가 실측한 잡 트랜잭션 경계를 그대로 쓰면 금지 패턴("트랜잭션 안 외부 API 호출")을 위반하게 되어, 상태 전이 트랜잭션과 결제 실행을 별도로 쪼개는 추가 설계가 필요 |
| 목표 미달 시 필요한 동작 | 환불 API 호출 + 실패 시 재시도 큐 | 없음 |
| 목표 달성 후 결제 실패 시 정합성 영향 | 없음(이미 결제 성공한 참여만 반영됨) | 결제 실패한 참여자를 어떻게 처리할지 별도 정책 필요 — 이미 `currentQuantity`에 포함되고 `FINISHED`로 확정된 뒤라, ADR-0002의 단조성 불변식("확정 상태는 되돌아가지 않음")을 건드리지 않으면서 실패분만 취소하는 방법이 필요 |
| 사전 요구사항 | 결제 즉시 승인(참여 시점에 카드 처리 완료) | 결제수단 토큰화/사전 등록(빌링키 등) 연동 필요 |

## 트레이드오프

**A 선택 시 감수할 점**
- 목표 미달 시 환불 API 신뢰성에 의존하고, 환불 실패에 대한 재시도/모니터링 로직이 필요하다.
- 미달 공구 종료 잡(ADR-0002가 실측한 A-1 경로)는 순수 상태 전이만 유지되어, 잡 처리 시간에 PG 왕복 지연이 얹히지 않는다.

**B 선택 시 감수할 점**
- 참여 트랜잭션에서 금지 패턴을 가장 깔끔하게 피할 수 있다.
- 대신 정산 배치가 상태 전이와 알림뿐 아니라 참여자 수만큼의 동기 결제 승인까지 맡게 된다.
  ADR-0002가 확정한 잡 트랜잭션 경계를 재설계해야 하고(상태 확정과 결제 실행을 별도 트랜잭션/스텝으로 분리),
  이 분리 설계는 이 ADR과 별개의 스코프다.

**공통 리스크**
- 결제가 실패한 참여자를 어떻게 할지는 두 모델 모두 피할 수 없다. A는 환불 실패, B는 승인 실패라는 형태만
  다를 뿐 재시도/예외 처리 정책이 필요하다.

## 결정

**B(목표 달성 후 결제)를 채택한다.**

- 환불 로직 자체가 없어지는 이점이 크고, 참여 트랜잭션(ADR-0001)에는 PG 호출이 전혀 섞이지 않아
  금지 패턴("트랜잭션 안 외부 API 동기 호출")을 구조적으로 피할 수 있다.
- 대신 정산 배치(ADR-0002)가 상태 전이뿐 아니라 참여자 수만큼의 결제 승인까지 책임지게 되므로,
  ADR-0002가 이미 확정한 잡 트랜잭션 경계를 "상태 확정"과 "결제 실행"으로 분리하는 설계가
  선행돼야 한다. 이 분리 설계는 되돌리기 어려운 트랜잭션 경계 결정이라 별도로 Plan Mode를 거쳐
  진행하고, 결과를 이 ADR 또는 후속 ADR(0004)에 반영한다.

## 참고 — 향후 실측이 필요한 하위 질문

이 ADR에서 A/B 중 하나로 방향이 정해지면, 다음은 ADR-0001/0002와 같은 방식(`ExecutorService` 기반
동시 호출 통합 테스트)의 실측이 필요한 후속 결정이다:

- B를 채택할 경우: 정산 배치의 결제 fan-out을 상태 전이 트랜잭션과 어떻게 분리할지(예: 상태만
  먼저 커밋하고 결제는 별도 비동기 잡/이벤트로 처리하는 구조), 그리고 그 분리 구조에서 결제
  실패 참여자를 취소 처리하는 로직의 동시성 안전성.
- A를 채택할 경우: 환불 실패 재시도 큐의 중복 실행 방지(ADR-0002의 B-1 패턴을 재사용할 수 있는지).
