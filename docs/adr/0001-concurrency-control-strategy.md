# ADR 0001: 공구 참여(재고 차감) 동시성 제어 전략

- 상태: 채택됨
- 작성일: 2026-09-08
- 관련 이슈: #5

## 배경

마감 임박 시점에 다수 사용자가 동시에 참여(결제) 요청을 보낼 때, `GoodsFunding.current_quantity`가
`target_quantity`를 초과하지 않도록 보장해야 한다. 단일 전략을 문서 조사만으로 정하는 대신,
AI로 세 가지 구현을 빠르게 스캐폴딩하고 동일 조건에서 실측 비교해 근거 있는 결정을 내린다.

## 비교 대상 구현

| 구현 | 방식 | 비고 |
|---|---|---|
| A. Redis 분산락  | 참여 요청마다 공구 ID 기준 락 획득 후 재고 차감 | 락 대기 시간, TTL 설정 필요 |
| B. DB 비관적 락  | 트랜잭션 내에서 GoodsFunding row 락 | 별도 인프라 불필요, DB 커넥션 점유 시간 증가 우려 |
| C. 낙관적 락 + 재시도  | 버전 충돌 시 재시도 로직 | 락 대기 없음, 충돌 많으면 재시도 비용 증가 |

## 실험 설계

- 부하 도구: ExecutorService 기반 동시 호출 통합 테스트. 서비스 메서드를 직접 호출해
  HTTP 계층 영향 없이 락 전략 간 차이만 비교하고, 종료 후 재고 정합성을 같은 테스트에서 검증한다.
  (아래 TPS·지연은 서비스 계층 기준 수치) (`src/test/java/com/goodsup/demo/orders/service/experiment/ConcurrencyLoadExperimentTest.java`,
  이후 채택 전략만 남기고 `OrderConcurrencyIntegrationTest`로 승격/정리)
- 인프라: MySQL 8.0 + Redis 7(alpine), 실행 환경 제약으로 Testcontainers의 Docker Engine API 접근이
  막혀 있어 실측 시에는 `docker run`으로 직접 띄운 동일 이미지의 컨테이너에 연결해 측정.
  (커밋된 테스트 코드 자체는 CI에서 정상 동작하는 Testcontainers 기반으로 유지)
- 시나리오: 목표 수량(N) = 50, 서로 다른 사용자 200명이 수량 1씩 동시 요청(M=200, N < M)
- 측정 지표: 재고 오차율(초과 판매 발생 여부), 처리량(TPS), 응답 지연(p50/p95/p99), 에러율
- 각 구현별로 동일 조건에서 3회 반복 측정 후 평균값 비교

|---|---|---|---|
| 재고 오차율 | 0% (초과 판매 없음) | 0% (초과 판매 없음) | 0% (초과 판매 없음) |
| TPS | 334.45 | **851.11** | 256.37 |
| 응답 지연 (p95) | 458.33ms | **132.33ms** | 772.67ms |
| 응답 지연 (p99) | 564.67ms | **148.33ms** | 798.33ms |

참여할 수 있었던 요청이 탈락한 것.

## 결정

**B. DB 비관적 락을 채택한다.**

- 세 전략 모두 재고 정합성(오버셀링 방지)은 동일하게 보장했으므로, 결정은 처리량·지연·에러율로 갈렸다.
- B는 TPS·p95·p99·에러율 네 지표 모두에서 가장 우수했다. 별도 인프라(Redis) 없이 이미 사용 중인
  MySQL 트랜잭션만으로 구현되어 인프라 실패 지점(Redis 장애/네트워크 지연)이 줄어든다.

## 트레이드오프

**A. Redisson RLock (탈락)**
- 장점: 인스턴스가 여러 개여도 락 범위를 넓게 잡을 수 있고, DB 트랜잭션과 무관하게 TTL을 짧게 유지할 수 있다.
- 탈락 이유: p95·p99 지연이 B의 3.5~3.8배(458ms vs 132ms, 565ms vs 148ms)였고,
  Redis 장애나 네트워크 파티션이라는 장애 지점이 추가된다.

**C. 낙관적 락 + 재시도 (탈락)**
- 장점: 읽을 때 row를 잠그지 않아 요청이 서로 기다리지 않는다. 충돌이 드물면 재시도 없이 한 번에 끝난다(저경합은 미측정).
- 탈락 이유: 마감 직전처럼 같은 row에 경합이 몰리면 재시도가 쌓여 지연과 에러율이 가장 나빴다.
  재시도 횟수를 늘리면 에러율은 줄겠지만 지연은 더 늘 것으로 추정된다.

**B를 선택하며 감수한 점**
- 트랜잭션이 끝날 때까지 row 락과 커넥션을 잡고 있다. 그 안에 외부 API 같은 느린 작업이 섞이면
  커넥션 풀이 고갈될 수 있다.
- 실험은 단일 인스턴스, HikariCP 기본 풀(10) 기준이다. 락을 기다리는 동시 요청 수가 풀 크기를 넘으면
  커넥션 대기가 생기므로, 인스턴스를 늘리거나 풀 크기를 바꿀 때 재검증이 필요하다.
