# ADR 0001: 공구 참여(재고 차감) 동시성 제어 전략

- 상태: 채택됨
- 작성일: 2026-09-08
- 관련 이슈: #5

## 배경

마감 임박 시점에 다수 사용자가 동시에 참여(결제) 요청을 보낼 때, `GoodsFunding.current_quantity`가
`target_quantity`를 초과하지 않도록 보장해야 한다. 단일 전략을 문서 조사만으로 정하는 대신,
AI로 세 가지 구현을 빠르게 스캐폴딩하고 동일 조건에서 실측 비교해 근거 있는 결정을 내린다.

## 비교 대상 구현

| 구현 | 방식 | 비고 |
|---|---|---|
| A. Redis 분산락 (Redisson RLock) | 참여 요청마다 공구 ID 기준 락 획득 후 재고 차감 | 락 대기 시간, TTL 설정 필요 |
| B. DB 비관적 락 (`SELECT ... FOR UPDATE`) | 트랜잭션 내에서 GoodsFunding row 락 | 별도 인프라 불필요, DB 커넥션 점유 시간 증가 우려 |
| C. 낙관적 락 + 재시도 (`@Version`) | 버전 충돌 시 재시도 로직 | 락 대기 없음, 충돌 많으면 재시도 비용 증가 |

## 실험 설계

- 부하 도구: **JMeter 대신 ExecutorService 기반 동시 호출 통합 테스트**로 대체.
  로컬 환경에 JMeter가 설치돼 있지 않고, CLAUDE.md가 이미 동시성 로직 검증 방식으로
  "ExecutorService 기반 동시 호출 테스트 또는 Testcontainers 활용"을 명시하고 있어
  별도 도구 설치 없이 동일한 측정 목적을 달성할 수 있다고 판단해 대체함.
  (`src/test/java/com/goodsup/demo/orders/service/experiment/ConcurrencyLoadExperimentTest.java`,
  이후 채택 전략만 남기고 `OrderConcurrencyIntegrationTest`로 승격/정리)
- 인프라: MySQL 8.0 + Redis 7(alpine), 실행 환경 제약으로 Testcontainers의 Docker Engine API 접근이
  막혀 있어 실측 시에는 `docker run`으로 직접 띄운 동일 이미지의 컨테이너에 연결해 측정.
  (커밋된 테스트 코드 자체는 CI에서 정상 동작하는 Testcontainers 기반으로 유지)
- 시나리오: 목표 수량(N) = 50, 서로 다른 사용자 200명이 수량 1씩 동시 요청(M=200, N < M)
- 측정 지표: 재고 오차율(초과 판매 발생 여부), 처리량(TPS), 응답 지연(p50/p95/p99), 에러율
- 각 구현별로 동일 조건에서 3회 반복 측정 후 평균값 비교

## 실험 결과

3회 반복 평균값 (전략 모두 최종 `currentQuantity`는 정확히 50으로 목표치와 일치 — 오버셀링 없음):

| 지표 | A. Redis 분산락 | B. DB 비관적 락 | C. 낙관적 락+재시도(최대 10회) |
|---|---|---|---|
| 재고 오차율 | 0% (초과 판매 없음) | 0% (초과 판매 없음) | 0% (초과 판매 없음) |
| TPS | 334.45 | **851.11** | 256.37 |
| 응답 지연 (p95) | 458.33ms | **132.33ms** | 772.67ms |
| 응답 지연 (p99) | 564.67ms | **148.33ms** | 798.33ms |
| 에러율 | 0% | **0%** | 9.83% (재시도 소진) |

실패로, 실제로는 참여 가능했어야 할 요청이 시스템 사정으로 실패한 것이라 사용자 경험상 문제가 된다.

## 결정

**B. DB 비관적 락(`@Lock(LockModeType.PESSIMISTIC_WRITE)` / `SELECT ... FOR UPDATE`)을 채택한다.**

- 세 전략 모두 재고 정합성(오버셀링 방지)은 동일하게 보장했으므로, 결정은 처리량·지연·에러율로 갈렸다.
- B는 TPS·p95·p99·에러율 네 지표 모두에서 가장 우수했다. 별도 인프라(Redis) 없이 이미 사용 중인
  MySQL 트랜잭션만으로 구현되어 인프라 실패 지점(Redis 장애/네트워크 지연)이 하나 줄어든다는 부수 이점도 있다.
- CLAUDE.md의 기존 "동시성 로직은 반드시 Redisson RLock을 사용한다" 원칙은 이번 실측 결과를 근거로
  이 유스케이스(공구 참여 재고 차감)에 한해 예외로 갱신한다(CLAUDE.md 아키텍처 원칙 항목 수정, 관련 커밋 참고).

## 트레이드오프

- **A. Redisson RLock (탈락)**: 여러 애플리케이션 인스턴스가 서로 다른 DB 커넥션 풀/트랜잭션을 쓰는
  구조에서도 잠금 범위를 넓게 가져갈 수 있고, DB 트랜잭션과 무관하게 락 TTL을 짧게 유지할 수 있다는
  장점은 있다. 그러나 이번 실측에서는 Redis 왕복 오버헤드 때문에 지연이 B의 3~4배였고, 별도 인프라
  (Redis 가용성, 네트워크 파티션 시 락 획득 실패)에 대한 장애 지점이 추가된다는 비용이 이점을 상회했다.
- **C. 낙관적 락 + 재시도 (탈락)**: 락 대기가 없어 저경합 상황에서는 유리할 수 있으나, 마감 임박
  시점처럼 동일 row에 대한 경합이 극심한 시나리오에서는 재시도 비용이 누적되어 지연과 에러율이
  가장 나빴다. 재시도 횟수를 늘리면 에러율은 낮아지겠지만 지연은 더 악화될 것으로 예상되어(관찰이 아닌
  추정이므로 참고만) 마감 정산처럼 경합이 몰리는 로직에는 부적합하다고 판단.
- **B를 선택하며 포기한 부분**: 비관적 락은 트랜잭션이 끝날 때까지 DB row 락과 커넥션을 점유하므로,
  락 보유 트랜잭션 안에서 외부 API 호출 등 느린 작업이 섞이면(이미 CLAUDE.md 금지 패턴이기도 함)
  커넥션 풀 고갈로 이어질 수 있다. 또한 이번 실험은 단일 인스턴스/소규모 커넥션 풀 기준이라, 인스턴스
  수나 동시 참여 대상 공구 종류가 크게 늘어나는 경우 재검증이 필요하다는 한계를 남긴다.
