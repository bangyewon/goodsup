# ADR 0006: PENDING 결제 상태 모델링 및 결제수단별 타임아웃 정책

- 상태: 부분 구현 (축 1·2·4 반영, 축 3·5 미구현 — 결정은 사람 확인 후 확정)
- 작성일: 2026-09-25
- 관련 이슈: #9
- 관련 ADR: [0001](./0001-concurrency-control-strategy.md), [0003](./0003-payment-timing-strategy.md),
  [0004](./0004-payment-fanout-trigger-strategy.md), [0005](./0005-partial-fanout-failure-refund-strategy.md)

## 배경

### 여기까지 오게 된 사고 과정 (순서대로)

이 ADR은 사람이 코드를 요청한 게 아니라, ADR-0005(부분 실패 취소·환불) 리뷰 중 사람이 던진 질문에서
출발한 대화로 도출됐다. 결론만 남기면 왜 이 설계를 택했는지가 사라지므로, 기각한 대안까지 포함해
순서대로 남긴다.

1. **문제 제기**: `targetQuantity`가 채워져 `FINISHED`가 확정돼도, fan-out 단계에서 일부 참여자의
   개인 결제가 실패하면 실질적으로 목표 수량을 채우지 못한 채로 끝난다. 이 위험을 어떻게 다룰지
   질문이 나옴.
2. **재모집(빈자리 다시 채우기) 검토 → 기각**: `FINISHED` 확정 후 빈자리를 다시 채우는 안은
   ADR-0002가 jqwik property test로 이미 고정해둔 "확정 후 상태 전이는 되돌아가지 않는다"
   불변식과 정면으로 충돌한다. 이 불변식 위에 ADR-0003/0004가 이미 쌓여있어 되돌리는 비용이
   크다고 판단해 기각.
3. **카드 hold/capture(사전 승인 후 나중에 확정) 검토 → 기각**: 참여 시점에 카드를 미리
   승인만 해두고(hold) 목표 달성 시 실제 매출을 확정(capture)하면 카드 문제는 참여 시점에
   걸러질 걸로 기대했으나, 두 가지로 기각됨:
   - 카드 hold는 보통 5~7일이면 자동 해제되는데, 공구 기간이 통상 1~2주라 더 늦게 채워지는
     공구는 capture 시점에 hold가 이미 풀려있을 수 있음(재승인 배치가 또 필요해져 복잡도만 증가).
   - **무통장입금(가상계좌)에는 hold라는 개념 자체가 없다** — 카드사처럼 잔고를 미리 묶어둘
     방법이 없고, 참여자가 실제로 이체해야만 결제가 성립한다. hold/capture는 카드에만, 그것도
     반쪽짜리로만 적용된다.
4. **참여 시점에 결제 확인을 앞당기는 안(개인별 결제 기한을 RECRUITING 중에 둠) 검토 → 보류**:
   참여 즉시 카드는 승인, 무통장입금은 가상계좌 발급 + 개인별 입금 기한(예: 24~48시간)을 주고,
   기한 내 미완료 시 그 참여만 자동 취소(아직 `RECRUITING`이므로 불변식 문제 없음)하는 안.
   목표 미달 위험을 구조적으로 줄이는 효과는 있지만, ADR-0003이 "참여 트랜잭션엔 PG 호출을
   넣지 않는다"고 정리해둔 경계를 다시 여는 큰 작업이라 **당장 채택하지 않고 향후 재검토 대상으로
   보류**한다(하단 "참고" 절).
5. **더 근본적인 선행 문제 발견**: 3~4번을 검토하는 과정에서, 위 어떤 안을 고르든 상관없이 먼저
   고쳐야 하는 문제가 드러났다. 현재 `PgChargeResult`(`success`/`failure` 이진)와
   `PaymentFanOutRelayScheduler`의 재시도 정책(작성 당시 `MAX_ATTEMPTS`=5, `BASE_BACKOFF`=10초,
   `MAX_BACKOFF`=10분, `LEASE_TIMEOUT`=5분 — 이후 ADR-0004의 실측+정책 결정으로 `MAX_ATTEMPTS`=11,
   `LEASE_TIMEOUT`=90분으로 확정됨. 전부 `payment/service/PaymentFanOutRelayScheduler.java`)은 **PG가 몇 초~몇 분 안에 성공/실패를 즉답하는 카드형 결제만 전제**하고 있다.
   무통장입금은 실제로는 "가상계좌 발급 완료, 아직 입금 안 됨"이라는 **제3의 상태(PENDING)**가
   존재하고 입금까지 며칠이 걸릴 수 있는데, 지금 모델은 이 상태를 표현할 방법이 없다. 이대로
   무통장입금을 붙이면 참여자가 입금할 시간을 기다려주지 않고 재시도 5회·백오프 최대 10분
   안에 **거의 전부 FAILED로 확정**돼버린다 — 개인의 결제 실패가 아니라 **시스템이 기다려주지
   않아서** 발생하는 실패라 4번보다 먼저, 반드시 고쳐야 하는 문제로 판단했다.

이 ADR은 5번(선행 문제)만 다룬다. 4번(참여 시점 검증)은 이 ADR이 자리잡은 뒤 실제로 목표 미달이
얼마나 남아있는지 보고 재검토한다(하단 "참고" 절).

## 비교 대상

이 ADR은 "A vs B 전략 비교"보다는 "무엇을 추가로 모델링해야 하는가"에 가깝다 — 기존 설계를
대체하는 게 아니라 빠진 축(결제수단, 대기 상태, 실패 사유 분류)을 채우는 확장이기 때문이다.

### 설계 축 1: PENDING 아웃컴 추가

`PgChargeResult`(`payment/dto/PgChargeResult.java`)에 `success`/`failure` 외 `pending`(또는 동등한
표현)을 추가해, PG 응답이 "아직 확정 안 됨"임을 표현할 수 있게 한다. `chargeOne`
(`PaymentFanOutRelayScheduler.java` 86-105행)이 이 아웃컴을 받으면 `markPendingForRetry`가 아니라
별도 경로로 처리해야 한다 — 지금처럼 실패로 취급해 재시도 카운트를 소모시키면 안 된다(입금 대기는
"시도가 실패한 것"이 아니라 "아직 안 끝난 것"이므로 `attemptCount`를 소모시키는 게 부적절).

### 설계 축 2: 결제수단(PaymentMethod) 모델링

`Payment` 엔티티에 결제수단 개념이 아예 없다. `CARD`/`VIRTUAL_ACCOUNT`(무통장입금) 같은 구분이
있어야 결제수단별로 다른 타임아웃 정책을 적용할 수 있다.

### 설계 축 3: 결제수단별 타임아웃 정책

- 카드: 지금처럼 짧은 재시도(초~분 단위)로 성공/실패를 빠르게 확정.
- 무통장입금: 입금 기한(예: 3일)까지는 `PENDING`으로 유지하고 재claim 대상에서 제외하거나
  훨씬 긴 주기로만 재확인, 기한이 지나야 비로소 `FAILED`로 확정.
- `PaymentFanOutRelayScheduler`의 `MAX_ATTEMPTS`/`BASE_BACKOFF`/`MAX_BACKOFF`가 지금은 전역
  상수인데, 결제수단별로 분리된 정책(전략 객체 또는 정책 테이블)으로 바꿔야 한다.

### 설계 축 4: 입금 확인 웹훅과의 연결

무통장입금의 `PENDING → SUCCEEDED` 전이는 결국 PG로부터 입금 확인 웹훅을 받아야 일어난다.
이슈 #9의 "결제 웹훅 수신 엔드포인트" 항목(아직 미착수)과 이 ADR이 맞물린다 — 웹훅이 오면
폴링 릴레이의 재claim을 기다릴 필요 없이 즉시 `PENDING → SUCCEEDED`로 전이시키는 경로가
있어야 사용자 경험상 자연스럽다(다만 폴링 릴레이만으로도 최종 정합성은 보장되므로, 웹훅은
지연을 줄이는 최적화로 볼 수도 있다 — 최종 결정은 웹훅 엔드포인트 설계 시점에 함께 정리).

### 설계 축 5: 실패 사유 코드화 및 재시도 가능 여부 분류

축 1~4를 검토하던 중, 카드 결제도 지금 설계가 놓치는 부분이 있다는 지적이 나왔다: 카드
잔액부족처럼 **재시도해도 결과가 달라지지 않는 실패**(사용자가 뭔가 하지 않는 한 1초 후든
5번 재시도 후든 똑같이 거절됨)와, PG 서버 타임아웃·네트워크 순간 장애처럼 **재시도가 실제로
의미 있는 실패**를 지금은 구분하지 않는다. `PgChargeResult.failure`(`payment/dto/
PgChargeResult.java`)가 `String errorMessage`만 갖고 있어 이 둘을 애초에 구분할 방법이 없다.

- `PgChargeResult`에 구조화된 실패 사유(예: `FailureReason` enum 또는 코드 필드)를 추가한다 —
  자유 텍스트 메시지만으로는 재시도 가능 여부를 코드가 판단할 수 없다.
  - 재시도 가치가 없는 사유(잔액부족, 카드 한도초과, 유효기간 만료, 카드 정지 등): 재시도
    없이 즉시 `FAILED`로 확정 — `markPendingForRetry`를 거치지 않는 새 경로 필요.
  - 재시도 가치가 있는 사유(PG 타임아웃, 네트워크 오류, 일시적 서버 오류 등): 기존처럼
    `markPendingForRetry`(축 3의 결제수단별 정책)를 그대로 탄다.
- 이 분류는 축 1(PENDING)과는 다른 축이다 — PENDING은 "아직 결과가 안 나온 상태", 이 축은
  "결과가 실패로 나왔을 때 그 실패의 성격"을 다룬다. 둘 다 `PgChargeResult`를 확장하지만
  서로 독립적인 필드/분기다.
- 부수 효과: 잔액부족처럼 재시도 무의미한 실패가 즉시 `FAILED`로 확정되면, ADR-0005의
  취소·환불 경로로도 그만큼 더 빨리 넘어간다 — 참여자 입장에서 "왜 5번이나 재시도하고 나서야
  실패라고 알려주지" 없이 더 빠르게 결과를 알 수 있다.
- 실제 PG SDK가 제공하는 응답 코드 체계(예: 포트원/토스페이먼츠의 실패 코드 목록)를 봐야
  "재시도 가능/불가능" 분류표를 정확히 채울 수 있다 — 지금은 `LoggingPgPaymentGateway`
  플레이스홀더 기준이라, 이 분류표 자체는 실제 PG 연동 시점에 확정하고, 이 ADR은 "그런 분류가
  구조적으로 가능해야 한다"는 모델링까지만 다룬다.

## 구현 현황 (코드·테스트로 확인한 사실, 2026-09-30 기준)

| 설계 축 | 상태 | 확인 근거 |
|---|---|---|
| 1. PENDING 아웃컴 | 반영됨 | `PgChargeStatus.PENDING`, `PgChargeResult.pending()`, `PaymentChargeExecutor.handlePending` → `ChargeOutcome.AWAITING_PG`. 릴레이는 `markPendingRecheck`로 재확인 시각만 미루고 `attemptCount`/`lastError`를 건드리지 않는다(`OutboxEvent.markPendingRecheck`). 통합 테스트 `B1`이 검증 |
| 2. 결제수단 모델링 | 반영됨 | `PaymentMethod{CARD, VIRTUAL_ACCOUNT}`, 참여 요청(`ParticipateGoodsFundingRequest`) → `Orders` → `Payment`로 전달. `B1`이 전달 여부를 assert |
| 3. 결제수단별 타임아웃 | **미구현** | 재확인 간격은 결제수단과 무관한 전역 상수 `PENDING_RECHECK_INTERVAL`=30분 하나뿐이고, 입금 기한 개념이 코드에 없다. 따라서 입금이 영원히 안 되는 `PENDING` 결제를 `FAILED`로 확정하는 경로가 없다 |
| 4. 입금 확인 웹훅 | 반영됨 | `POST /api/payments/webhook`(HMAC-SHA256 서명 검증) → `PaymentService.applyWebhookResult`(`findByIdForUpdate`). 웹훅의 `PENDING` 상태는 무시한다 |
| 5. 실패 사유 코드화 | **미구현** | `PgChargeResult.failure`는 여전히 `String errorMessage`만 가지며, `handleFailure`는 사유와 무관하게 항상 `RETRY_NEEDED`를 반환한다 |

`B1`은 실패 시나리오를 찾는 적대적 테스트가 아니라 축 1의 기대 동작을 확인하는 테스트다(무통장입금
PENDING이 재시도 예산을 소모하지 않고 재확인만 예약되다가 입금 확인 후 정상 종결). 아래 "실험 설계"의
1~4번은 아직 실측하지 않았다.

## 실험 설계 (구현 후 실측 필요 — CLAUDE.md "AI를 검증 파트너로 활용" 절차)

구현 후 `PaymentFanOutRelayConcurrencyTest`와 유사한 통합 테스트로 다음을 재현·실측한다:

1. `PENDING` 상태의 결제가 lease 재claim 로직과 충돌 없이 동작하는가(ADR-0004의 claim/lease
   메커니즘을 그대로 재사용할 수 있는지, 아니면 `PENDING` 전용 처리 경로가 필요한지).
2. 결제수단별로 다른 타임아웃이 같은 outbox 릴레이 안에서 서로 간섭 없이 분기되는가(카드 건이
   무통장입금 건의 긴 대기 때문에 지연되지 않는지, 또는 그 반대).
3. 무통장입금 입금 기한이 지나 `FAILED`로 확정된 결제가 ADR-0005의 취소·환불 경로로 올바르게
   이어지는가.
4. 재시도 불가 사유(예: 잔액부족)로 분류된 실패가 `markPendingForRetry`를 거치지 않고 즉시
   `FAILED`로 확정되는가, 그리고 재시도 가능 사유로 분류된 실패는 기존처럼 결제수단별 정책을
   따르는가(축 5).

재현 여부와 무관하게 모든 시나리오를 `docs/experiments/adversarial-test-log-payment.md`에 기록한다.

## 결정 (초안)

*(사람 확인 후 확정.)*

- **축 1·2·4는 이미 코드에 반영됐으므로 이 ADR의 결정으로 추인한다**: PENDING은 실패가 아닌 "미완료"로
  다루어 재시도 예산을 소모시키지 않고, 결제수단은 `Payment`에 저장하며, 입금 확인은 서명 검증된 웹훅으로
  받는다(폴링 재확인은 정합성 보루, 웹훅은 지연 단축).
- **축 3·5는 미구현이라 결정을 보류한다.** 구현 방식(결제수단별 정책 객체 vs 정책 테이블, 입금 기한
  값, 실패 사유 분류표)은 사람이 정해야 하고, 분류표는 실제 PG SDK 응답 코드가 필요하다.

## 트레이드오프

**확인된 것(코드·`B1` 테스트 근거)**
- PENDING을 별도 아웃컴으로 분리해, 입금 대기가 재시도 예산(`MAX_ATTEMPTS`)을 소모해 조기에 `FAILED`
  되는 원래 문제(배경 5번)는 축 1 범위에서 해소됐다.

**알려진 공백(미실측 — 가설이며 재현 전에는 결론 내리지 않는다)**
- 입금 기한이 없어 입금되지 않는 `PENDING`이 무기한 30분 간격 재확인 대상으로 남을 수 있다
  (축 3 미구현의 직접 결과로, 코드상 확정된 사실).
- `PENDING`이 하나라도 있으면 릴레이는 같은 outbox row 안의 다른 결제(예: 실패한 카드 건)에 대해서도
  `markPendingForRetry` 대신 30분 간격 재확인으로 처리한다(`processOne`의 `anyAwaitingPg` 분기).
  카드 재시도가 결제수단이 다른 건의 대기에 묶이는지는 실험 설계 2번으로 **재현해야 확인된다.**
- 재시도 무의미한 실패(잔액부족 등)도 재시도 경로를 타 `FAILED` 확정과 ADR-0005 환불 경로 진입이
  늦어진다(축 5 미구현).

*(실험 설계 1~4 실측 후 이 절을 갱신하고 상태를 "채택됨"으로 바꾼다.)*

## 참고 — 향후 재검토가 필요한 하위 질문

- **참여 시점 결제 확인 앞당기기(위 4번, 보류)**: 이 ADR(PENDING 모델링 + 결제수단별 타임아웃)이
  자리잡은 뒤, 실제 운영 데이터로 "그래도 목표 미달이 얼마나 남는지" 확인하고, 여전히 유의미하게
  남는다면 그때 ADR-0003 재검토 규모의 작업으로 착수한다.
- **ADR-0005와의 실행 순서**: ADR-0005(부분 실패 취소·환불)는 "최종 실패가 확정된 이후" 무엇을
  할지를 다루고, 이 ADR은 "언제 최종 실패로 확정할지"를 다룬다 — 즉 이 ADR이 ADR-0005보다 먼저
  구현돼야 순서가 맞는다(무통장입금을 지원하기 전까지는 ADR-0005만으로도 카드 기준 동작에는
  문제없다).
- 이슈 #9의 "PG 테스트(샌드박스) 연동" 항목에서 실제 PG(포트원/토스 등)가 무통장입금 응답을
  어떤 형태(동기 PENDING 응답 vs 비동기 웹훅만)로 주는지에 따라 설계 축 1~4가 조정될 수 있다 —
  현재는 `LoggingPgPaymentGateway` 플레이스홀더 기준으로만 설계된 가정임을 유의.
